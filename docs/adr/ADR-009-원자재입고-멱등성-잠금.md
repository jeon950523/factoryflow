# ADR-009 — 원자재 LOT 입고의 멱등성 및 잠금 정책

- **기준일:** 2026-11-11
- **상태:** 구현 초안에 적용 / MySQL 실검증 전
- **관련:** [SSOT v0.1](../FACTORYFLOW_SSOT_v0.1.md), [TASK-003B 보고서](../task-reports/TASK-003B-원자재입고-구현-검수.md)

## 의사결정과 이유

1. **단일 MySQL 트랜잭션:** 신규/기존 LOT 수량 변경, `stock_receipts`, `stock_movements` 기록이 모두 성공해야 커밋한다. 일부 성공은 잘못된 재고와 감사 이력 불일치를 일으킨다.
2. **품목(Item) 행 선잠금:** `ItemRepository.findForUpdate`가 먼저 잠근다. 같은 원자재에 대한 여러 요청을 직렬화하여 LOT 신규 생성 및 수량 누적의 동시성 위험을 낮춘다. 이후 생산지시 예약/출고도 이 잠금 규칙을 따른다.
3. **`READ_COMMITTED`:** 락을 획득한 후 `requestKey`를 다시 조회했을 때 이전 요청의 커밋 결과가 보여야 한다. 기본 격리 수준과 실제 동작 비교는 DB 통합 테스트 후 확정한다.
4. **정규화된 멱등성 키와 요청 해시:** `requestKey`, `lotCode`를 앞뒤 공백 제거 및 `Locale.ROOT` 대문자로 통일한다. 입력 단계에서 ASCII 문자 집합(`A-Z, a-z, 0-9, ._:-`)만 허용해 Unicode 대문자 변환 충돌을 막는다. SHA-256 해시는 `itemId`, LOT 코드 길이·값, `quantity`를 바탕으로 만든다. **요청 동등성 확인용이지 서명/인증 수단이 아니다.**
5. **실패한 트랜잭션 바깥에서 재조회:** `StockReceiptService`(트랜잭션 없는 오케스트레이터) → `StockReceiptWriteService`(쓰기 트랜잭션) → `StockReceiptLookupService`(새 읽기 트랜잭션)로 나눴다. `UNIQUE(request_key)` 경합 시 재조회는 이전 실패 트랜잭션 안에서 하지 않는다.
6. **DB UNIQUE + CHECK:** `request_key` 유일성, `inventory_lots(item_id,lot_code)` 유일성, 예약고/현재고 부등식을 DB가 최종 방어한다.
7. **REST 응답:** 최초 201 + `Location: /api/v1/stock-receipts/{id}`, 동일 키·동일 내용 재전송은 200 + 동일 내용, 동일 키·다른 내용은 409. `Location`의 조회가 가능하도록 SSOT v0.1 API 초안에 없던 GET `/stock-receipts/{id}`를 추가한다.

## 대안과 트레이드오프

| 선택 | 장점 | 단점 / 보완 |
|---|---|---|
| **Item 행 선잠금** (채택) | 같은 품목의 LOT 경쟁 처리가 단순하고 잠금 순서 설명 용이 | 품목별 병렬 처리량 감소, 긴 트랜잭션에 취약. 실제 경쟁 테스트·성능 측정 필요 |
| LOT 행만 잠금 | 서로 다른 LOT의 병렬 처리에 유리 | LOT 최초 생성 레이스 및 다중 LOT 작업 잠금 순서 관리가 어려움 |
| Redis 분산 락 | 여러 DB/서비스 간 조정에 활용 가능 | 단일 MySQL MVP에는 복잡도와 장애 지점만 증가 |
| 사전 중복 조회만 사용 | 구현 단순 | 동시 요청에서 두 요청 모두 조회에 실패할 수 있어 안전하지 않음 |
| 하나의 `@Transactional` 메서드에서 UNIQUE 예외 잡아 재조회 | 코드량 감소 | 실패 트랜잭션의 rollback-only 상태 / 현재 트랜잭션 읽기 불안정 위험 |
| JDBC 조건부 UPDATE | 고경합에 유리할 수 있음 | 여러 LOT·명세서·이력의 일관된 트랜잭션 구현을 따로 유지해야 함 |

## 제한 및 후속 검증

- 실제 Docker/MySQL/Gradle 테스트는 현재 실행 환경에서 미실행이다. 2개 동시 입고, 같은 키 재시도, 전혀 다른 품목에서 같은 키 충돌, 강제 실패 롤백을 **실제 DB**로 확인해야 한다.
- 선잠금 때문에 같은 품목의 입고만 연속 처리된다. 이후 **T-05/T-06 예약 동시성**과 함께 처리량 비교가 필요하다.
- 대규모 전체 품목 재고 합계는 `BIGINT` 범위를 넘어갈 수 있다. 조회 시 `BigDecimal.longValueExact()`로 조용한 잘림을 막지만, 초대형 수량 도메인에는 `DECIMAL` 모델 검토가 필요하다.
- 조회 API는 다중 쿼리로 페이지 총건수와 데이터를 가져오므로 그 사이에 입고가 발생하면 페이지 메타가 순간적으로 달라질 수 있다. 정산이나 금융원장 수준의 원자적 스냅샷을 요구한다면 별도 읽기 정책 필요.
- 인증/인가가 없으므로 외부 인터넷 공개 금지. `server.address=127.0.0.1` 유지.
