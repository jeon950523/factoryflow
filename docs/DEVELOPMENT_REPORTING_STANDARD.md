# FactoryFlow — 개발 작업 기록 규칙 v1.0

> 적용일: 2026-11-11  
> 대상: TASK-002 이후 모든 개발·수정·리팩터링 작업  
> 상태: 작업 기록 운영 규칙 (코드 구현 완료를 의미하지 않음)

## 1. 목적

FactoryFlow는 AI 도구를 사용해 개발하더라도 **개발자가 의도·설계 근거·코드 실행 흐름·검증 증거·한계·개선 계획을 스스로 설명할 수 있어야 한다.** 단순 구현 체크리스트가 아니라 **판단과 검증의 이력**을 남긴다.

한 TASK의 완료 기준은 `구현됨`이 아니라 `구현 + 재현 가능한 검증 + 설명 가능`이다. 다만 실행 환경 제약으로 검증을 못 했다면 보고서는 작성하되 TASK는 `검증 대기`로 둔다.

## 2. 파일 구조와 명명

```text
docs/
├─ DEVELOPMENT_REPORTING_STANDARD.md        # 이 규칙
├─ templates/
│  └─ TASK_REPORT_TEMPLATE.md               # 새 작업 보고서 원본
├─ task-reports/
│  ├─ TASK-002-개발기반-구축.md               # 기존 검수·학습 문서를 하나로 통합할 때 작성
│  ├─ TASK-003-품목-BOM-입고.md               # 이후 예시
│  └─ ...
├─ adr/
│  └─ ADR-XXX-선택주제.md                    # 대안과 트레이드오프가 있는 설계 변경만 별도 기록
└─ TROUBLESHOOTING.md                        # 실제 발생·재현한 문제만 기록

tasks/
└─ TASK_XXX_작업지시서.md                     # 구현 전 작업 범위·완료 기준
```

- `tasks/`: **무엇을 할 것인가** (작업 전)
- `docs/task-reports/`: **무엇을 했고 왜 그렇게 했으며 어떻게 검증했는가** (작업 후)
- `docs/adr/`: **여러 대안 중 왜 특정 설계를 골랐는가** (중요한 설계 변경 시)
- `docs/TROUBLESHOOTING.md`: **실제로 발생한 장애를 어떻게 진단하고 해결했는가** (문제 발생 시)
- SSOT는 시스템의 현재 규칙을 기록한다. 작업 보고서는 의사결정과 변경 이력을 기록한다. **문서 간 사실이 충돌하면 근거·ADR·테스트를 통해 먼저 정리**하고 임의로 덮어쓰지 않는다.

## 3. 모든 TASK 종료 시 필수 작성 순서

1. **목적·배경:** 어떤 문제를 해결하며, 기존 기능과 어떻게 연결되는가.
2. **구현 범위·상태:** 완료 / 부분 완료 / 검증 대기 / 보류를 기능별로 구분한다.
3. **전체 호출 흐름:** 실제 메서드·HTTP 경로·트랜잭션·DB 조작 순서(가능하면 코드 심볼 기준).
4. **변경 파일별 해설:** 정확한 경로, 핵심 책임, 해당 코드/구조를 선택한 이유, 기존 코드와 연결점을 설명한다.
5. **핵심 코드 설명:** 중요한 1~3곳에 대해 코드 또는 짧은 diff, 입력→처리→출력, 대안 및 선택 이유를 설명한다. 코드를 그대로 붙이는 데 그치지 않는다.
6. **예외·경계조건:** null/유효성, 중복 요청, 경쟁 상태, 롤백, 권한/보안, 성능·운영 위험 중 해당하는 항목을 다룬다.
7. **검증 결과:** 실제 실행 명령, 환경·버전, 테스트 케이스, 성공/실패 로그 또는 경로, 미실행 사유를 명시한다. **테스트 코드를 작성한 것과 통과한 것은 다르다.**
8. **시니어 검수:** 기능·보안·트랜잭션·데이터 정합성·성능·가독성·유지보수성 점검 결과와 남은 위험을 적는다.
9. **장점과 단점:** 선택의 이점과 비용을 같은 맥락에서 비교한다. 대안을 최소 하나 검토한다.
10. **리팩터링 판단:** `즉시 수정` / `다음 TASK 전에 수정` / `2차 개선` / `현 시점 불필요` 중 하나를 **각 항목마다** 부여하고 근거, 관련 파일, 검증 조건을 적는다.
11. **설명 연습:** 20~40초 요약 및 스스로 답할 수 있어야 할 이해 점검 질문 1~3개. **면접 예상 질문과 답변은 요청받았을 때만** 제공한다.
12. **다음 작업 연계:** 의존성, 보류 이슈, 다음 TASK의 시작 조건을 남긴다.

## 4. 사실·추측·계획 분리 규칙

- `검증됨`: 실제로 실행하거나 저장소에서 확인한 증거가 있을 때만 사용.
- `정적 검토`: 코드·스키마·구문을 검토했지만 실행 검증을 하지 않은 경우.
- `미검증`: 코드 존재 여부와 무관하게 런타임 결과를 확인하지 못한 경우.
- `설계 가정`: 근거가 있으나 실측이나 실서비스 검증이 필요한 판단.
- `향후 계획`: 현재 코드로 제공되지 않는 기능.

성과 표현에서 위 단계를 섞지 않는다. 테스트 성공률·성능 향상률·지연 시간 등 수치는 **로그/측정 조건 없는 임의 숫자 사용 금지**.

## 5. 코드 검수 및 리팩터링 판단 기준

| 점검 관점 | 반드시 확인할 질문 |
|---|---|
| 기능 | 요구사항·상태 전이·불변조건을 지키는가? |
| 정확성 | 동일 요청 반복, 부분 실패, 동시 실행에서 결과가 일관적인가? |
| 데이터 | 트랜잭션 경계, FK/UNIQUE/CHECK, N+1, 락 순서에 문제가 없는가? |
| 예외 | 오류 코드, 원인 추적, 민감정보 누출 방지가 적절한가? |
| 효율 | 실제 병목 근거 없이 Redis/캐시/병렬화 등을 넣지 않았는가? |
| 설계 | Controller/Service/Repository 책임, DTO-Entity 경계가 명확한가? |
| 유지보수 | 중복, 과도한 추상화, 테스트하기 어려운 결합이 있는가? |
| 검증 | 변경을 입증하는 자동 테스트·수동 재현 절차가 있는가? |

리팩터링은 '언젠가 개선'이라고만 적지 않고, **지금 수정하지 않는 이유**도 명시한다. 기능 오류·데이터 손상·보안 위험은 미뤄둘 개선 항목이 아니라 우선 수정 대상이다.

## 6. Git 운영

- TASK당 목적 단위로 커밋하며 **한국어 커밋 메시지**를 사용한다.
- 기능 코드와 TASK 보고서의 연결은 commit SHA 및 변경 파일 목록으로 남긴다.
- 보고서는 검수 후 같은 TASK의 작업물로 관리한다. 검증 미완료 TASK를 완료로 표시하지 않는다.
- **원격 push는 사용자 명시적 요청/승인을 받은 경우에만 수행한다.** 로컬/작업 산출물 작성과 원격 게시를 구분한다.
- 민감한 비밀번호·API 키·개인정보·내부 인프라 정보를 문서와 로그에 포함하지 않는다.

## 7. TASK-002 기록의 현재 사실

TASK-002 관련 기존 문서는 다음 두 개이다.

- `docs/TASK_002_구현_및_검수_기록.md`: 변경 이유, 전체 흐름, 장단점, 미검증 현황, 리팩터링 계획
- `docs/TASK_002_학습가이드.md`: 파일별 역할, 코드 선택 이유, 예외·테스트, 직접 설명할 요약

이 둘은 **이미 작성된 기록**이며, 추후 새 템플릿으로 통합할 때 기존의 `Gradle 빌드·MySQL 실기동·Testcontainers 미검증` 사실을 유지해야 한다.
