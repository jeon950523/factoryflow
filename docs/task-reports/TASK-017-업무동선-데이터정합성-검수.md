## 1. 검수에서 확인한 원인

1. 생산지시 목록의 **지시번호 버튼**은 `choose(id)`를 호출하지만 URL에 `id`를 기록하지 않아, 새로고침하면 선택이 사라졌다. 같은 행의 **상세 보기 링크**는 `/orders?id=...`를 사용해 사용자 조작 방식에 따라 복원 여부가 달랐다.
2. 생산지시·출고의 목록 페이지는 로컬 상태였고, 페이지 이동 후 새로고침 시 첫 페이지로 돌아갔다. 이전에 복원 가능한 `?id` 주소에서 페이지를 바꿀 때는 오래된 `id`가 URL에 남을 수 있었다.
3. BOM의 원자재, 생산지시 원자재, 완제품 출고 배분과 재고 이동 이력이 독립 화면으로 구현되어 있어 실제 물리 LOT 재고와 업무 이력을 추적하려면 사이드바를 거쳐 매번 품목을 다시 찾아야 했다.

## 2. 구현 및 업무 계약

- `OrdersView.vue`: 번호 클릭과 상세 링크 모두 `orderLink(id)`를 사용. 상태 필터·페이지와 선택 ID를 URL에 보존하고, 목록 페이지 변경 시 옛 선택 ID를 제거한다. 완제품을 품목/BOM·현재 LOT 재고·이동 이력으로, 원자재별로 LOT 재고·이동 이력으로 연결한다.
- `ItemsView.vue`: BOM 원자재별로 실제 해당 원자재의 LOT 재고 조회 링크를 제공한다.
- `InventoryView.vue`: 선택한 품목의 실제 LOT 현황에서 같은 품목의 물리 재고 이동 이력으로 연결한다.
- `ShipmentsView.vue`: 출고 상세의 실제 LOT 배분과 현재 LOT 현황을 유지하고 해당 품목의 이동 이력 링크를 추가한다. 출고 목록의 페이지·선택 ID를 URL에서 복원하며 페이지 전환 시 이전 상세 ID를 제거한다.
- 모든 링크는 실제 서버가 제공하는 품목 ID, 생산지시 ID, 출고 ID만을 사용한다. 없는 LOT 코드, 존재하지 않는 예약 상세, 과거 재고 잔량을 추정하지 않는다.
- 표시상 **현재 LOT 잔량**과 **과거 물리 이동 이력**을 분리한다. 재고 예약/해제는 물리 이동에 포함하지 않는다.
- 링크와 새 조회 방식은 VIEWER 조회 전용 정책을 변경하지 않는다.

## 4. 시니어 코드 검수

**기능성:** 서로 다른 화면/버튼의 선택 동작을 동일한 URL 계약으로 통일해 재현성을 개선한다. 생산지시의 원자재 소요량은 주문 생성 시점 BOM 스냅샷이며, 재고·이동 이력은 현재/과거 원장을 각각 서버에서 조회한다. 서로 다른 데이터의 의미를 혼합하지 않는다.

**안전성:** API 요청 필드, 역할별 쓰기 권한, FIFO·재고 예약·품질검사 처리를 수정하지 않는다. 모든 새 링크는 read-only 조회 URL이다. 테스트용 실제 DB 데이터는 기존 CI MySQL에서만 생성한다.

**경쟁 상태:** 기존 `createLatestRequest` / RouterView `route.fullPath` 기반 리마운트 동작을 유지하고, URL 페이지·ID 변경 시 이전 조회 취소가 발생한다. 기존 비동기 선택 최신 요청 우선 테스트를 회귀 실행한다.

**효율성:** 조회용 링크로만 연결하여 새로운 전역 상태나 별도의 재고 집계를 만들지 않는다. 상세 자료를 화면 사이에 복제하지 않고 기존 서버 계약에 재조회한다. 동일한 URL 페이지 파서는 추후 공통 유틸리티로 정리할 수 있으나 MVP에서 즉시 추상화할 필요는 없다.

**잔여 개선:** 많은 데이터에서 20건 이상 이력 페이지 이동, 창고 다중화, LOT/재고 변동 장부의 서버 기간별 검색은 별도 기능 계약이 필요하다. 운영 Vercel에 최신 코드가 배포됐는지와 PC 화면 시각·키보드 검수는 PR 단계 CI와 별도 확인한다.
